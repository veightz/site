日常研究里，最容易踩的坑不是「记不住」，而是过早搭系统：还没有几篇站得住脚的文章，就开始设计目录、双向同步、内容中间表示和专用编辑器。结果工具越来越重，真正能单独拿出来读的知识却很少。

本文记录一套更克制的工作方式：**先沉淀解决独立问题的优质内容，等出现明确的知识依赖和教学需求后，再组织专题教材**——不以文章数量或固定周期强制课程化。

## 五条原则

1. **先产出内容，再建设系统。** 日常研究先落到可演进的收件箱（例如 GitHub Issues），优先写成能单独阅读的博客；教材是后续编排，不是起点。
2. **博客与教材并行，但不共用一套叙事。** 博客承载观点、实践和阶段性发现；教材承载系统化学习路径。事实、代码、图解和交互组件可以复用，叙事结构不必强行统一。
3. **一份知识，多种 View（视图）。** 用 Git / Markdown 管理稳定内容与资源，按需输出 Interactive Document（交互文档）、Slide View（演示视图）、Lab View（实验视图）。双链、知识图谱和专用笔记编辑器不是初期必需能力。
4. **人审、版本化、按需发布。** AI 可以辅助提炼或生成可视化组件，但正式内容必须核验事实、检查安全并固定版本——不应依赖每次阅读时实时调用模型。
5. **探索空间与执行上下文分离。** 用于探索、沉淀和创作的草稿，不应未经核验就混进 Agent 的共享执行知识；两边可以互通，但要有明确边界。

## 最小工作流：Capture → Refine → Compose → Publish

| 阶段 | 做什么 | 刻意不做 |
| --- | --- | --- |
| **Capture（捕获）** | 明确要沉淀某次讨论后，按「问题同一性」更新已有记录、追加阶段评论，或新建关联条目 | 不是每段聊天都建一条 |
| **Refine（提炼）** | 定期筛选有价值的条目，核验依据，产出可单独阅读的 Markdown 博客 | 不把收件箱原文当最终发布物 |
| **Compose（编排）** | 相关主题积累够了再做教材大纲；按概念难度选择性加入图解、Explorable Explanations（可探索式解释）或 Scrollytelling（滚动叙事） | 不为完成形式而逐级加可视化 |
| **Publish（发布）** | 正式博客 / 教材与组件源码进 Git；视图独立构建、选择性公开 | 不自动把草稿仓库整仓暴露到公网站点 |

现阶段通常只需要：**收件箱 + Markdown + 少量可复用 Widget**。复杂目录、Content IR（内容中间表示）、双向同步或自研编辑器都可以往后放。

## 几项技术取舍

**收件箱 → Markdown，而不是把收件箱当发布物。** Issue 一类工具适合收集与演进记录；正式内容需要稳定的 Markdown（或 MDX）形态，便于审查、版本化和站点构建。

**Git 作为正式内容源。** 自定义 HTML/JS、源码与版本更适合放在 Git 里。协作文档（例如飞书）可以当输入端，但往返转换的保真度（表格、代码块、图像、特殊块）需要抽样验证，不宜默认双向同步。

**HTML 沙箱 vs 受约束 UI DSL。** 前者适合快速 PoC；后者适合规模化治理。是否引入编译 / Runtime，取决于复用规模与安全需求——没有复用压力时，不必提前上平台。

**可视化按需使用。** 收件箱默认精炼 Markdown；教学场景才根据概念难度选用 Mermaid、动画或交互模拟。图形要能降低理解成本，而不是装饰。

## 和「交互式表达」的衔接

当一篇博客开始反复解释因果、参数影响或时间过程时，纯文字会显得吃力。那时再考虑 Explorable Explanations、Distill 式图表论证或 Scrollytelling——交互是为了理解，不是为了热闹。表达方式的选择另文展开。

## 下一步可以验证什么

1. 用一篇真实技术博客试做可复用 Widget，并在文档视图与演示视图中复用，观察维护成本、内容一致性和移动端体验。
2. 观察几周的捕获与整理效率，再决定要不要引入自动分类或定期提炼；不强制每周一篇。
3. 若用协作文档作输入源，抽样测试关键块类型的 Round-trip Fidelity（往返转换保真度）。
4. 交互组件发布前检查脚本权限、外部网络、可访问性与离线加载行为。
